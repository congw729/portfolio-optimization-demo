## 二、问题清单（按严重度分级）

### 🔴 阻塞级（1 项，需 Leader 决策）

**B-1. 方式 1「当前团队 spawn」与当前团队成员架构不匹配，5 角色演示无法落地（位置：§5 方式 1 与落地检查清单）**
- 问题：方式 1 声称「在当前团队任务看板创建 T1–T5，teammate 认领执行；角色=任务认领者+职责」，并引用「本项目 P1–P3 就是这么做的」作为已实测依据。但按当前团队名册，执行型成员仅 **dev-engineer 与 dev-engineer-2 2 人**（team-leader 不承接执行任务、portfolio-planner 明确不负责执行）；而验收标准 A4 要求「演示中能清楚看到 ≥4 个 agent 通过任务看板与消息衔接」。2 名执行成员无法呈现 5 角色协作画面：① 系统约束「同一时刻只能有一个进行中任务」，单成员只能串行认领，无法同时承载多个角色任务（2 人最多并行 2 个角色，仍缺 3 个角色承载者）；② M1–M6 消息流是成员间通信，若由同一成员先后扮演多个角色，send_message 衔接失去「协作」语义，演示效果退化为 2 人接力脚本；③ P1–P3 已实测的只是「leader 拆任务 → teammate 认领 → 汇报」的单/双链路，不能外推为 5 角色协作链路已可行。
- 依据：团队成员名册（4 人，执行型 2 人：dev-engineer、dev-engineer-2）；准备清单 v1.1 验收 A4；§5 方式 1 描述与落地检查清单（无成员就绪项）。
- 修改建议：**需 Leader 决策**，三选一：
  - a) 扩展现有团队至 ≥4 个执行型 teammate（或确认演示时可注入演示角色成员），并在落地检查清单首项加入「5 角色认领人（成员）就绪」；
  - b) 升级方式 2（独立演示团队预注册 5 角色）为主路径，并提前实测 config.yaml `agents` 段 teammate 注册 schema（对应评审 I-1 ⚠️ 项）；
  - c) 明确降级备选：若团队架构不扩展，则以「dev-engineer 串行认领 T1–T5 + 方式 3 确定性脚本」为现场形态，但需向课程方说明演示定位为「单 agent 串行 + 脚本流水线」而非多 agent 协作（降低 A4 预期或调整验收口径）。

### 🟠 重要级（3 项，建议定稿前修订）

**I-1. T1 data-collector 任务定义遗漏基线（stocks）数据拉取（位置：§1.1 ↔ §1.3/§4.1）**
- 问题：§1.1 任务内容、输入输出、对接脚本均只覆盖方案 A 六只 ETF + rf + 基准（SPY），未提基线 6 只个股；但 §1.3 optimizer 输入依赖 `data/params_stocks.json`、`data/returns_stocks.csv`，§4.1 目录布局也列有 `closes_stocks.csv / returns_stocks.csv / params_stocks.json`——基线数据链路无任务归属，T3 的基线运行将因缺数据而失败。
- 依据：§1.1 输出列（4 个文件，无 stocks 系）；§1.3 输入列（含 params_stocks.json / returns_stocks.csv）；§4.1 目录布局。
- 修改建议：在 §1.1 任务内容与输出中明确「同时拉取基线 6 只个股（复用 fetch_data.py `--name stocks`），产出 closes_stocks.csv / returns_stocks.csv / params_stocks.json」，并在对接脚本命令中补 stocks 命令。

**I-2. T3→T2 依赖语义与 T3 输入集合不一致（位置：§2.1 ↔ §1.3）**
- 问题：T3 blocked_by T2（严格）的理由是「需要 params 与 features……保证派生特征一致」，但 §1.3 的输入列**不含 features.json**（仅 params.json / params_stocks.json / returns 两 CSV）——依赖链声称的「features 依赖」在数据流上没有体现，依赖语义落空；若 optimizer 实际不用 features.json，则 T3 依赖 T2 只是形式化的串行化，且 M2 消息内容（「features.json 已就绪……请开始优化」）也隐含了 T3 应消费 features。
- 依据：§2.1 T3 行「需要 params 与 features；实际仅需 T1 产物」；§1.3 输入列无 features.json；§3 M2 消息内容。
- 修改建议：二选一——a)（推荐）将 features.json 纳入 T3 输入（如 60/40 基准参数用于组合对比、corr 矩阵供优化前校验），使依赖名副其实；b) 若 optimizer 确实不需要 features，将 T3 依赖改为 T1，允许 T2/T3 并行（但会削弱「流水线接力」演示语义，不推荐）。需向作者确认 optimizer 实际消费哪些特征。

**I-3. 「步骤 5 负相关示例事实错误」— 已撤回（误判）**
- 原判：§6 步骤 5 写「相关矩阵含负相关（DBC-GLD -0.12）」，我认为 GLD 与 DBC 应为正相关 0.3–0.4，与 v1.1 §5.1 矛盾，判为事实错误。
- 复核结果（依据 P2b 实测数据 `p2-data-report.md` §5 相关矩阵）：实测 **GLD-DBC = -0.12（负相关）**、**SPY-TLT = +0.68（正相关）**——P4a §6 步骤 5 引用的 -0.12 与实测数据**一致**，引用正确；方案 A 的负相关元素实际是「商品-黄金（GLD-DBC）」，而非股债。我此前依据 v1.1 §5.1 的**预估值**（GLD/DBC 相关 0.3–0.4，原文已标「⚠️ 需实测」）作判断，未核实 P2b 实测数据，属误判。
- 结论：**I-3 正式撤回**。P4a §6 步骤 5 无需修改；连带修正：v1.1 准备清单 §5.1 中 GLD/DBC 与 SPY/TLT 相关性描述为预估值，建议随 P4b 回写为实测值（GLD-DBC = -0.12、SPY-TLT = +0.68，并将「负相关出现在股债」的描述更正为「负相关出现在商品-黄金（GLD-DBC）」）。

### 🟡 建议级（4 项）

**S-1. 共享目录同步方案表述前后矛盾，未收敛单一推荐（位置：§4.1）**
- 问题：同一段先写「推荐把项目目录内 data/ output/ 与 .team/ 对应子目录做符号链接或同步」，末尾又写「简化起见……以 .team/ 为唯一共享真相源，脚本通过 --data-dir / --output-dir 参数指向该目录」——两处推荐不一致；且脚本是否已支持 --data-dir/--output-dir 未核实（P2a/P3 脚本实际参数以 dev-engineer 实现为准）。
- 修改建议：收敛为单一推荐（建议 `--data-dir/--output-dir` 参数方案：无跨目录符号链接风险、git 状态清晰；符号链接列为备选），并把「三个脚本均需支持 --data-dir/--output-dir」作为对 dev-engineer 的显式工程要求标注 ⚠️ 验证。

**S-2. params_assetclass.json 与 params.json 双文件关系未说明（位置：§1.1 ↔ §4.1）**
- 问题：§1.1 输出列含 `params_assetclass.json` 与 `params.json`（正式参数文件）两个文件，但 §4.1 目录布局仅列 `params.json`（及 params_stocks.json），二者关系（内容是否相同、为何两份）未交代。
- 修改建议：明确「params_assetclass.json 为带方案标识的原始输出，params.json 为统一正式文件名（或删除冗余，统一为 params.json）」，并在目录布局中保持一致。

**S-3. §2.1 DAG 图中 T5 双入边表达易误读（位置：§2.1 图）**
- 问题：图中 `T3 ──► T4 ──► T5` 与 `T3 └──► T5（T4 完成后）` 并存，T3→T5 的直连边标注「（T4 完成后）」易被误读为「T4 完成后才触发 T3→T5」；表格 T5 行已正确写「blocked_by T3 + T4」。
- 修改建议：图中改为单链 `T1→T2→T3→T4→T5`（T3→T5 依赖隐含于链路）或明确双入边标注「T5 blocked_by T3, T4」，与表格一致。

**S-4. M4 消息措辞与 T5 依赖约束有轻微冲突（位置：§3 M4）**
- 问题：M4（optimizer→reporter）内容写「可开始汇总」，但 T5 blocked_by T3+T4，reporter 实际需等 viz（T4）完成才能开工；虽然看板机制保证 reporter 不会提前认领，但消息措辞与依赖语义不一致。
- 修改建议：M4 措辞改为「产出已就绪（待 T4 完成后汇总）」，并在消息流说明 reporter 以 M5 为开工触发点。

## 三、亮点确认

1. **「脚本即任务实现 + 产物即接口」双原则**：把 LLM 不确定性限制在决策/衔接层（读什么、跑哪个命令、传给谁），每个 agent 的任务收敛为「调一个已测脚本 + 产出约定文件」，现场稳健性有工程级保障，是整份设计的灵魂。
2. **角色任务定义五要素完整**（内容/输入/输出/对接脚本/关键校验），feature-engineer 与 reporter 无独立脚本的可行性自述诚实（增量价值=派生特征/汇总报告），并给出沉淀小脚本（features.py/report.py）的路径，⚠️ 标注到位。
3. **DAG 与看板机制精确对应**：先指派 T1、下游 blocked_by 逐级解锁，与 jiuwenswarm 任务看板实际机制一致，看板本身即可视化 DAG，演示价值高。
4. **消息流 M1–M6 全覆盖且遵守「路径+摘要 ≤2000 字符」约束**，教学点（上下文解耦、不搬运数据）提炼准确。
5. **落地方式三选一对比表维度完整**（成本/演示效果/现场风险/教学契合），推荐「方式 1 主 + 方式 3 兜底」符合现场稳健性优先约束；方式 2 弃用理由（未实测、重启影响当前会话）成立。
6. **现场 11 步流程含教学点与时长预算**（核心 15 + 缓冲 5 ≤ 25min，满足 S-3），风险预案三连（LLM 卡顿→方式 3、断网→缓存、任务失败→重派）对应准备清单坑 #9。
